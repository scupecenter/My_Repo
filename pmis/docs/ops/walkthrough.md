# Feature walkthrough on the real stack

Why: the web e2e suite runs on the in-browser mock API, so it cannot prove database rules (guard triggers, SQL doors, RLS, If-Match, audit rows). This runbook starts the real API on a scratch PostgreSQL database with the web app pointed at it, so a Playwright run exercises the feature end to end. Every PR checklist has a Walkthrough step (below).

## One call
Needs PostgreSQL 16 listening on `127.0.0.1:5433` with trust auth for the superuser `postgres` (override with `PG_HOST`, `PG_PORT`, `PG_SUPER`), `psql`, node 22 and Chrome.

    cd pmis && tools/walkthrough/start.sh     # about 90 s the first time; prints READY api:3000 web:5174
    tools/walkthrough/stop.sh

What it does, in order: `builddb.sh` creates `pmis_walk` (every prisma migration in order, one transaction per file, `app_grants.sql`, the 7 regions; the same steps as `apps/api/test/global-setup.ts`), `seed.cjs` installs the context key and bootstraps one System Admin (employee id `9001`, password `Walk-Admin-Pass-2026`, test-only), the API is built (`npm run build`; do not run it with `tsx`, which drops the decorator metadata Nest needs) and started detached on :3000 with `~/walk/api.env` (random test-only keys generated by `start.sh` on first run), and Vite starts on :5174 with `VITE_USE_MOCKS=false` and `VITE_PROXY_TARGET=http://127.0.0.1:3000`.

Processes started with `setsid nohup ... &` survive the end of a tool call. Logs: `~/walk/api.log`, `~/walk/web.log`.

## Run a spec against it

    cd pmis/apps/web
    WALK=1 PW_CHROMIUM_PATH=/usr/bin/google-chrome npx playwright test e2e/walk.spec.ts

`e2e/walk.spec.ts` is skipped unless `WALK=1`. Copy it per feature (`walk-<feature>.spec.ts`, same guard): sign in as 9001, change the Setting through its real door, use the feature, take screenshots (`test-results/`), also in Arabic (`localStorage pmis.locale = ar`). Check the database after: `psql -h 127.0.0.1 -p 5433 -U postgres -d pmis_walk -c "select action, reason from audit_log order by id desc limit 5"`.

After you change a migration or the API: run `start.sh` again (it rebuilds the database and the API).

## Limits
- Only the System Admin exists. Create other users and data through the API or SQL in your spec when the feature needs them (the API tests have helpers in `apps/api/test/helpers.ts` and `dash-seed.sql`).
- Pages that exist only in the mock (no real route yet) answer 404 here; say so in the PR instead of skipping silently.
- Jobs (`JOBS_ENABLED=false`), mail and malware scan are off.

## PR checklist step: Walkthrough
1. A Playwright spec for the feature in EN and AR: Setting change through the real door, the effect on the screen, the permission-denied case.
2. Screenshots of each state attached to the PR; the audit row seen in the database.
3. Run on the real stack (this runbook) for anything that touches the database; on the mock only for pure layout.
4. List every place covered and every place deliberately excluded, with the reason.
