# ADR 0014: Two-factor authentication (TOTP) for local accounts

- Status: Accepted, 2026-11-02. Owner decision of 2026-11-02 (CLAUDE.md, CHANGELOG 59). Closes "TOTP is later" of ADR 0012.
- Amended 2026-11-02 (same day): one-time enrolment code, see "Amendment 1" below. Migration `0034_totp_enrol_code` (`db/sql/033_totp_enrol_code.sql`), contract 0.6.0.
- Amended 2026-11-02 (later): self-service on, conditional self-service off, "enforced by admin". See "Amendment 2" below. Migration `0044_self_service_profile` (`db/sql/043_self_service_profile.sql`), contract 0.9.2. It replaces the last two sentences of item 2.
- Related: ADR 0012 (local sign-in), ADR 0002 (authentication, step-up), ADR 0003 (`idm_*` paths), migration `0033_totp_two_factor` (`db/sql/032_totp_two_factor.sql`), contract 0.5.0.

## Decision
1. **Code.** RFC 6238 with HMAC-SHA-1, 6 digits, 30 seconds, one step either side. Implemented with node crypto (`apps/api/src/auth/totp.ts`) and tested with the vectors of RFC 6238 Appendix B and RFC 4226 Appendix D. The time is an argument, so tests do not depend on the weekday or the machine clock.
2. **Who decides.** Only a System Admin, or a delegate holding the delegable right `users.two_factor` (stored as the delegation grant `users.administer`, all regions), turns it on or off for a user, or resets it. Needs a reason and the actor's own step-up. Nobody changes their own setting through the admin path, an admin included: `idm_two_factor_guard` refuses it in the database. A delegate cannot change an admin or another delegate (`idm_assert_user_change_allowed`). The user needs a local account. *(Amendment 2: users may now turn it on themselves, and off unless an admin enforced it.)*
3. **Turning it on.** The user's local sessions end at once (otherwise a session would live on without a code) and the user enrols at the next sign-in. **Turning it off** deletes the secret and the recovery codes. **Reset** (lost phone) deletes both, forces a new enrolment and ends all sessions. Every change is audited with before and after (`two_factor`, `recovery_codes_remaining`, `sessions_ended`); never a secret.
4. **Sign-in.** The password check does not create a session when two-factor is on. It creates a pending sign-in (`auth_pending`: SHA-256 of a random token, 5 minutes, single use) and sets the cookie `pmis_2fa` (HttpOnly, SameSite=Strict, path `/api/v1/auth/local/2fa`). `next` is `two_factor` (call `POST /auth/local/2fa`) or `enrol` (no authenticator yet: the enrolment endpoints). Nothing else accepts that cookie.
5. **Enrolment** (changed by Amendment 1: it needs the enrolment code). `enrol/start` makes a 20-byte secret, stores it encrypted as the pending secret and returns the base32 key and the `otpauth://` URI (issuer "GSDN PMIS"); the web app draws the QR code in the browser. `enrol/confirm` checks the first code against the pending secret, activates it, makes 10 recovery codes (shown once), consumes the pending sign-in and signs the user in.
6. **Secrets at rest.** The secret is encrypted by the API with AES-256-GCM before it reaches the database. The key is `TOTP_ENC_KEY` (32 bytes, 64 hex characters or base64) from the server environment; the user id is the authenticated data, so a ciphertext copied to another row does not decrypt. The installer generates the key like `LOG_HMAC_KEY` and keeps it on update. Losing the key means every enrolled user must be reset and enrol again.
7. **Recovery codes.** 10 codes of 10 characters (50 bits, no look-alike letters). Stored as HMAC-SHA-256 with a key derived (HKDF) from `TOTP_ENC_KEY`. The API never reads the hashes: `auth_totp_use_recovery` matches and consumes in the database. A code works once and can replace a TOTP code at sign-in and at step-up. The number left is in `Session.two_factor`. New codes need a valid TOTP code (not a recovery code).
8. **Replay and lockout.** `user_totp.last_step` is the last accepted time step; `auth_totp_result` accepts a step only if it is greater, in one atomic `UPDATE` (two parallel uses of one code give one session). Wrong codes are counted apart from wrong passwords (a right password must not reset the code counter). Five in a row lock the account for 15 minutes through the same `local_credentials.locked_until`, and end every pending sign-in. Every failure is written to the System Log (`local_two_factor_failed`).
9. **Step-up.** For a user whose two-factor is on, `step_up_required` carries `step_up_method = password_totp`, and `POST /auth/local/step-up` needs the password and a code (or a recovery code). A missing code is 422 and nothing is counted.
10. **Database guard.** `auth_session_create` (migration 0014, replaced here) refuses a session for a user whose two-factor is on unless (a) a password check succeeded in the last 6 minutes, (b) a code success was recorded after it, in the last minute, and (c) a pending sign-in was consumed in the last minute. `pmis_app` has no table right on `user_totp`, `user_recovery_codes` or `auth_pending`. The residual risk is the one of ADR 0012: the API checks the code, so a fully compromised application role could still call `auth_totp_result(.., true, ..)`; the signed session context of P1-DB-03 closes it.
11. **First admin.** The bootstrap admin has two-factor off. Nobody can change their own setting, so a second System Admin turns it on for the first. If a two-factor admin loses the phone and no other admin exists, the operator runs `sudo bash tools/install/reset-two-factor.sh <email> [--disable]` on the server (it calls `idm_installer_reset_two_factor` and, for a reset, prints a new enrolment code; see Amendment 1).

## Amendment 1 (2026-11-02): a one-time enrolment code
**Gap closed.** In the first version a user whose two-factor was on but not set up enrolled with the password alone (trust on first use): someone who knew the password and signed in before the user's first enrolment could put their own authenticator on the account. Owner decision: a password alone must never enrol a phone.

1. **Issuing.** When a System Admin (or a delegate holding `users.two_factor`) turns two-factor on, or resets it, the API makes a one-time code and returns it once in the answer (`enrol_code`, `enrol_code_expires_at`; never cached, never logged). Format: 8 characters of the 32-letter alphabet without look-alikes (no 0, 1, I, O), shown as `XXXX-XXXX` (40 bits). The admin hands it to the user in person or by phone. Turning it on or resetting needs the reason and step-up that these calls always needed.
2. **Storage.** The API sends the database only a keyed hash: HMAC-SHA-256 over `<user id>:<code>`, key derived (HKDF, own label `pmis-enrol-codes`) from `TOTP_ENC_KEY`, like the recovery codes. The hash and its end time sit in `user_totp.enrol_code_hash` and `enrol_code_expires_at`. `pmis_app` has no right on `user_totp` (the `REVOKE ALL` of 0033 stays), so it cannot read the hash; it reads only `auth_totp_enrol_code_state` (the end time, no hash). The user id is part of the hashed text, so the code of one user matches nobody else. A table check allows a code only while the user is on and not enrolled.
3. **Lifetime.** The setting `two_factor.enrol_code_hours` (default 72, kept between 1 and 720, seeded by 0034). An expired code is refused with its own error.
4. **A new code.** `POST /users/{id}/two-factor/enrol-code` (`idm_issue_two_factor_enrol_code`), for a user in `pending_enrolment` only (409 otherwise). Same rights as the toggle, a reason, the actor's step-up, never for oneself. The old code stops working, a half-made enrolment is dropped and the user's pending sign-ins end. Audited as `two_factor_enrol_code_issued` with the old code's state (none, active, expired), never a code.
5. **Using it.** The code is asked at both steps. `enrol/start` takes `enrol_code` and the database checks it before anything else (`auth_totp_begin_enrol` returns `ok`, `bad`, `expired` or `locked`): without a right code no secret is made, none is stored and the QR code is never shown. `enrol/confirm` takes `enrol_code` again and the database checks it again in the same function that activates the secret and clears the hash (`auth_totp_confirm_enrol`), so the code is single use and consumed at the confirm. The first sign-in that started an enrolment still keeps it for 10 minutes (`pending_owner`).
6. **Failures.** A wrong or expired code counts toward the same counter as a wrong TOTP code: five in a row lock the account for 15 minutes (the password lock) and end every pending sign-in. The functions return the outcome instead of raising, so the count is not rolled back. A missing code is 422 and counts for nothing. Errors: 401 `invalid_enrol_code`, 401 `enrol_code_expired`, 429 `account_locked`. Failures go to the System Log (`local_two_factor_failed`, `via: enrol_code`) without the code.
7. **Installer reset.** `idm_installer_reset_two_factor(email, disable, code_hash)` now needs the hash of a new code unless it switches two-factor off. The database never holds the key, so `node dist/cli.js enrol-code <user-uuid>` (reads `TOTP_ENC_KEY`) makes the code and its hash, and `tools/install/reset-two-factor.sh` calls the function and prints the code once with its end time. The installer's closing message points to the script.
8. **Replaced functions.** `auth_totp_begin_enrol`, `auth_totp_confirm_enrol`, `idm_set_two_factor`, `idm_reset_two_factor` and `idm_installer_reset_two_factor` changed arguments or result, so migration 0034 drops their old forms (they were granted to `pmis_app` and would have enrolled without a code) and creates the new ones with the same owner and grants.
9. **Existing installations.** A user who is waiting for enrolment when 0034 runs has no code (the database cannot make one). Enrolment is refused until an admin issues a code (item 4).

**Residual risks and trade-offs.** (a) Someone who knows the password can still burn the five tries and lock the account for 15 minutes (a denial of service, the same as with wrong TOTP codes; the lock ends by itself and an admin can issue a new code). (b) With 40 bits and five tries per 15 minutes a guess is not realistic. (c) The admin sees the code on screen, so the hand-over channel matters: in person or by phone, never chat or email. (d) The pending sign-in (5 minutes) must be created by a right password first; the code does not replace the password, it adds a second proof that only the admin and the user know.

## Amendment 2 (2026-11-02): self-service on, conditional self-service off, "enforced by admin"
**Owner decision.** Two-factor is free to turn on and conditional to turn off. Any local user turns it on from "My profile"; the user may turn it off unless an admin enforced it.

1. **Turning it on yourself** (`POST /me/two-factor/enrol/start`, `/confirm`; `auth_totp_self_begin_enrol`, `auth_totp_self_confirm_enrol`). Needs a full signed-in **local session** and a **fresh step-up of that session** (password, within `stepup_max_age_seconds`), which the database checks again from `user_sessions` (`auth_self_session_ok`), not only the API. The secret is made and encrypted exactly as in item 5 and 6 (AES-256-GCM, `TOTP_ENC_KEY`, user id as authenticated data) and stored as the pending secret owned by that session (`pending_owner = 'session:<id>'`, 10 minutes); only that session can confirm it, with the first code (a wrong code counts toward the lock of item 8). On confirm two-factor is on and **not enforced**, 10 recovery codes are made (item 7), the user's other sessions and pending sign-ins end, and the current session is marked as having passed a code. Audited `two_factor_self_enabled`.
2. **Why no enrolment code here.** Amendment 1 closes trust on first use at **sign-in**, where the only proof is a password. The self path never runs at sign-in: it needs a live session (which already passed the password, and the code when one was set) plus a step-up of that same session. Someone who knows only the password cannot reach it without first signing in, and a user whose two-factor is already on cannot start it again (409); an admin reset still goes through Amendment 1 (a reset user waits for enrolment with an admin code). The admin path with the enrolment code stays unchanged for users an admin turns on.
3. **Enforced by admin.** `user_totp.enforced`. Turning it on through `PUT /users/{id}/two-factor` sets it, also for a user who had turned it on themselves (that call then only marks it, without a new code). `PUT /users/{id}/two-factor/enforced` (`idm_set_two_factor_enforced`) marks or unmarks it on its own: same rights and guard as the toggle (System Admin or a delegate holding `users.two_factor`, all regions; never one's own account; a delegate never for an admin), a reason and step-up, audited `two_factor_enforced` / `two_factor_unenforced`. A check keeps it false while two-factor is off (a trigger clears it on every path, the installer reset included). Every row that was on when 0044 ran was turned on by an admin, so all start enforced.
4. **Turning it off yourself** (`POST /me/two-factor/disable`, `auth_totp_self_disable`). Refused with 403 `two_factor_enforced` while enforced, before anything is counted. Otherwise it needs the **password and a TOTP code or a recovery code**: the API checks both with the usual functions (`auth_local_result`, `auth_totp_result` / `auth_totp_use_recovery`, counted toward the same locks, replay-guarded), and the database refuses unless a password success and, after it, a code success were recorded for this user in the last minute. The secret, the recovery codes and pending sign-ins are deleted; audited `two_factor_self_disabled`. A stolen open session alone therefore cannot remove the second factor.
5. **Unchanged.** Regenerating recovery codes (item 7), the sign-in and step-up flows (items 4, 9), the session guard of item 10 (`auth_session_create` is not touched: once on, every new session needs the code), the installer reset (item 11) and the admin reset.
6. **Rights of the application role.** `pmis_app` still has no table right on `user_totp`; it calls the new functions, each limited to the signed-in user's own row (`app.user_id` and `app_actor()`), and reads only `auth_totp_enforced` (a boolean, no secret).

**Residual risks.** (a) A user who is not enforced can lower their own protection to the password; the owner accepts it, and the admin enforces where it matters. (b) A stolen session with a fresh step-up (that is, also the password) can turn two-factor on with the thief's phone for a user who had it off; that user was protected by the password only, the change ends the other sessions (the real user notices at once) and is audited, and an admin reset recovers the account. (c) The residual risk of item 10 (a fully compromised application role) is unchanged.

## Consequences
- Local sign-in gets a second factor without Entra; M365 sign-in is unchanged (Conditional Access still applies there).
- A deployment needs `TOTP_ENC_KEY` in `pmis.env` before the API starts (the API refuses to start without it).
- The admin must keep a second System Admin if the first uses two-factor.
- Turning two-factor on or resetting it is a hand-over: the admin passes a code to the user. A user who loses it, or lets it expire, asks the admin for a new one.
- (Amendment 2) A user may turn two-factor on without the admin; an admin who needs it to stay on enforces it.
