# GSDN Workspace — project rules for every agent

GSDN Workspace is a project management information system for the GSDN site-delivery
project (telecom sites across 7 Libyan regions). It replaces the Excel Site Master
as the system of record, with a two-level approval workflow on every task: L1 Data Entry and L2 Data Reviewer & Approver (owner decision 2026-11-01).

All paths below are relative to `pmis/` unless marked as repository root. The previous standalone dashboard is kept read-only in `docs/reference/legacy-dashboard/` as the reference for dashboard KPIs (P3) and the pipeline style: do not modify it.

Read before any work:
1. `docs/reference/GSDN_Workspace_Blueprint_v1.1.html`: the functional blueprint (sections 03, 06, 14, 17, 21).
2. `docs/reference/GSDN_Rebuild_Decisions.md`: decisions D1–D88 that define the Master logic.
3. `GSDN_Site_Master.xlsx` (repository root): the Master structure (23 sheets, 187 columns). It is the source for field names and calculations.
4. `docs/spec/` (written by domain-analyst) and `contracts/openapi.yaml` (owned by tech-lead).

## Domain facts (do not change without an ADR)
- Default workflow (seed version 1; milestones and gates are admin-configurable, see Configuration): 10 milestones in this order: Site Release, PRE-CW Completion, CW Completion, Site RFI, TE Completion, On-Air, TE PAC, KPI Acceptance, HOTO, Final Closure.
- 9 phase gates between them. A gate date equals the previous milestone date. A Suspension→Resumption in Change Control shifts it.
- SLA counts working days. The weekend is Friday and Saturday (NETWORKDAYS.INTL code 7). Holidays come from a table.
- **Holidays are managed in Settings → Work calendar (decision B12).** The System Admin, or a delegate, can add, edit, delete and import holidays (date, name EN/AR, kind national/religious, "tentative" flag) and the weekend days, without code. Seed: `db/seed/holidays-2026-2027.csv`; religious dates are tentative until the admin confirms them on the official announcement, and the screen reminds the admin of tentative dates 14 days ahead. Every change is audited with before/after values and a reason. A change recalculates SLA due dates of open tasks; closed tasks keep their computed values. A banner shows while the table for the coming year is empty.
- Delivery Scenario: New Build, Expansion, Hot Swap, Cold Swap, Relocation. Overall Status: Not Started, In Progress, On Hold, Completed, Cancelled.
- Regions: Tripoli, Middle, WM, Zawia, Benghazi, GM, Sebha.
- Roles (owner decision 2026-10-29): roles are flat, with no main/sub-role split. Seed: Project Manager, RF & Design / Acquisition Team Lead, CW Team Lead, TE Team Lead, Inventory Supervisor, Project Support, RF Engineer, MW Engineer, Acquisition Team, Power Engineer, GECOL Power Team, HLC Fiber Team, Site Engineers (CW), Site Engineers (TE), HOTO Engineer, Project Procurement Team and Management. Names and properties are editable in Roles & Responsibilities.
- Aljeel supervising engineers (AAT SE) only supervise. TE installation steps through On-Air are the TE vendor's (A&T Global) responsibility.

## Workflow rules (agreed with the product owner)
- Login uses a local PMIS account now (ADR 0012) and the company Microsoft 365 account (Entra ID SSO) once IT registers the app. Each user is linked to a 4-digit employee ID.
- **One sign-in box, M365 does the sign-in (owner decision 2026-10-25).** The login screen has one field: the employee types their email, employee ID or registered phone. GSDN Workspace looks it up in the staff registry, keeps the match server-side, and sends the browser to Microsoft 365; Microsoft performs the actual sign-in (password, MFA, Conditional Access). For privacy, the registry email is never put in the redirect: Microsoft pre-fills the account only when the employee typed their email; with an ID or phone they pick or type their account on the Microsoft page, and GSDN Workspace checks on return that it is the same person. On this M365 path GSDN Workspace never sees the password (local accounts are below). To avoid revealing who is registered, the screen behaves the same whether or not a match is found (no match = Microsoft sign-in without a hint). After the callback, the token's account must match the registry row that was looked up; otherwise the normal first-sign-in link rules apply.
- **Local sign-in is built now; M365 comes later beside it (owner decision 2026-10-28, ADR 0012, replaces "deferred").** A System Admin (or a delegate) creates the account in Users & Roles with a temporary password, returned once; the user must change it at the first sign-in. The one sign-in box takes the employee ID, email or phone, plus the password. Every failure gives the same message; 5 failures lock the account for 15 minutes. **Two-factor (TOTP) for local accounts (owner decision 2026-11-02):** a code from an authenticator app (RFC 6238, 6 digits) after the password, and again at step-up. A System Admin (or a delegate granted it) turns 2FA on or off for a user, with a reason and their own step-up, never for their own account. **Self-service (owner decision 2026-11-02, ADR 0014 amendment 2):** any local user may turn 2FA on themselves from "My profile" (a full signed-in session plus a fresh password step-up; no admin enrolment code), and may turn it off with their password plus a TOTP or recovery code, **unless an admin enforced it**: turning 2FA on as an admin marks it "enforced by admin", and the admin can also mark or unmark it (reason, step-up, audited); while enforced, self-disable is refused (403 `two_factor_enforced`). A user whose 2FA is on but not yet set up must enrol (QR code) at the next sign-in before doing anything else, and gets one-time recovery codes. **A password alone can never enrol a phone (owner decision 2026-11-02):** turning 2FA on or resetting it gives the admin a one-time enrolment code (8 characters, XXXX-XXXX, shown once, valid 72 hours by default, setting `two_factor.enrol_code_hours`) that the admin hands to the user in person or by phone; the user enters it before the QR code is shown, a wrong code counts toward the same 15-minute lock as a wrong TOTP code, it works once, and the admin can issue a new one (reason and step-up, audited). The admin can reset a user's 2FA (lost phone), which forces a new enrolment with a new code. The secret is encrypted at rest; every change is audited and shown as a badge on Users & Roles. When M365 is added both methods stay: M365 is the main one, and the admin can turn local sign-in off per user or for everyone. The first System Admin is created by the installer on the server.
- **My profile (owner decision 2026-11-02, migration 0044; owner decisions 2026-11-04, migration 0058).** Each user edits their own display name, language and theme (audited with before/after); employee ID, email, status, roles, team, regions, department and manager stay admin-owned. **Changing the email is a request**: the user submits the new email with their password, it waits as pending, and a System Admin or a delegate holding `users.edit` for all regions approves or rejects it with a reason (never their own); only an approval changes the login email, uniqueness is checked, admins and the user are told in the inbox, and the user may cancel while pending. **The new address is verified first (Q158):** a one-time code is mailed to it and the user enters it in the profile; without it the admin may approve only after recording the documented identity check. The old and the new address are told by mail, without sensitive data. **Changing the phone is also a request (D156), because the phone is a sign-in identifier:** the same rules as the email (password, one pending request per user, uniqueness checked, decided by a System Admin or an all-regions `users.edit` delegate, never their own, audited, the user is told, cancel while pending); the phone is no longer self-edited. The password change from the profile needs the current password, follows the same policy and lock as sign-in, ends the other sessions and is for local accounts only (an M365 user sees a note). **An approved email change ends all of the user's sessions** (the email is a sign-in identifier; a phone change keeps them; technical decision Q303, migration 0066). **Turning two-factor off (Q161)**, by the user or by an admin, ends the user's other sessions (all of them for an admin "off"), deletes the recovery codes and sends a security notice.
- **Two approval levels, fixed rule (owner decision 2026-11-01).** Every task, register record and Dismantle part has exactly two levels: **L1 = Data Entry** (enters the data and submits) and **L2 = Data Reviewer & Approver** (reviews and approves; the decision is final; a rejection returns to L1 with a mandatory note). There are no other levels and the number of levels is not configurable. Who holds L1 and L2 is chosen in Roles & Responsibilities and the Responsibility Matrix. **A person (or role or group) can be granted L1 only, L2 only, or both L1 and L2 together** — an explicit option in Roles & Responsibilities; when the same person holds both, their submission is the final approval under the self-approval rule (B5: step-up, flagged in KPIs and the audit log, shown in advance on the matrix screen). **Exception (owner decision D230b, 2026-11-04): QC snags have no self-approval** — whoever raised, found or fixed a snag can never approve its closure or decide its evidence (403 `self_approval_forbidden`, migration 0056).
- Changing who holds a level applies to new tasks and to open tasks not yet submitted. A task snapshots its holders at first submission and finishes on them, including after a rejection sends it back to L1 (decision B7, adapted).
- The Responsibility Matrix (editable in the UI) decides who holds L1 and L2, per stage. If one person holds both levels, the self-approval rule (B5) applies and is logged.
- Matrix rows for registers and Dismantle (decision B11): besides the stage rows, the matrix has one row per register (Procurement PR/PO/WO, GECOL, HLC, Permits & HSE, Warehouse, Quality, Issue, Risk, Change Control, Readiness & Handover, As-Built, Meetings, Contractors, Car Dispatcher, Financial Advances) and one row for Dismantle. Each row has its own L1 and L2 holders, set by the admin.
- The unit of approval is the whole task: dates plus documents.
- A rejection goes back from L2 to L1 and must carry a note. Every task has a comment thread.
- Rejection of a self-approval (decision B6, adapted): when one person holds L1 and L2, a later reopening or rejection by an admin returns the task to that person at L1 with the note; resubmission is again a self-approval and is logged again.
- Batch uploads can be approved row by row or all at once.
- **Staff absence and reassignment (decision B12b).** Nothing moves automatically when someone is absent. The assigned person stays on the task until their Team Lead (or anyone with the `reassign` grant for that module and region, or a System Admin) decides. The lead has three choices per task, per site, or for all of the person's open tasks:
  1. keep the person on it;
  2. reassign it to another eligible person (a task-level holder change; the Responsibility Matrix itself is not changed);
  3. act on it themselves through the system, logged as "lead on behalf of the assignee".
  A reassignment needs a short reason and is audited. It keeps all entered data, documents and comments. **It does not reset or pause anything:** the SLA keeps its original start date and its SLA version, and stage progress is unchanged. If the lead takes over L1 and also holds L2, the self-approval rule (B5) applies.
  Absence records are optional and informational: an employee can record annual leave in advance, and the lead or an admin records sick or emergency leave. An absent person's tasks show an "absent" badge, and the lead is alerted. Separately, a task idle for N working days (default 2, a setting) alerts the lead even when no absence was recorded.
- **Deactivated or deleted users (decision B14, 2026-10-26).** Deactivating or soft-deleting an account (reason and step-up MFA required; no hard delete of the row, amended 2026-11-12: a System Admin may permanently delete an already soft-deleted user with reason, step-up and typed confirmation; the account leaves lists and cannot sign in, its email, employee ID and phone are released for a new account, and the users row stays as a tombstone so past entries, audit rows and task history remain attributed; the last-admin guard applies) ends its sessions but moves nothing: its open tasks stay on the person with a "deactivated" badge, the Team Lead is alerted at once and uses the B12b choices (keep, reassign, act on behalf), and a level left with no eligible active holder goes to the System Admins' inbox as "no holder" (B10). The SLA never pauses or resets. A deleted account can be restored with its previous assignments, unless its employee ID or email now belongs to another account. The last-admin guard applies.
- Visibility defaults to everything. It can be limited per user to one or more of the 7 regions and to selected modules.
- Data entry works three ways: manual entry, upload of the Master as an approved template, or upload of other approved templates. Every upload goes through batch → L2.
- **Approved templates only.** The system issues each template with an ID and version embedded in the file (hidden sheet `_tpl` containing `template_id` and `version`). A user downloads the template from beside the task or from the Templates page, fills it, and uploads that same template. Uploads without a valid embedded ID and version are rejected. Each rejection is written to the System Log.
- Registers are separate modules, each with its own menu: Procurement (PR/PO/WO), Contractors, GECOL power, HLC fiber, Permits & HSE, Warehouse, Quality, Issue Log (several issues per site), Risk Register, Change Control, Readiness & Handover, As-Built, and Meetings. RF & Design and Acquisition, which are sheets in the Master, are registers too.
- **Field assignments, Car Dispatcher and Financial Advances (owner decisions 2026-11-07, Q495–Q512, plan `docs/plans/2026-11-07-assignments-fleet-advances.md`).**
  - There is **no separate assignments register**: the Procurement record is the assignment, for companies (PO/WO, Outsourced or TE Vendor) and for internal teams (internal work order, In-House). Field work without a PO/WO (Survey, Acquisition Visit, Inspection, Maintenance, Emergency) is a Procurement record with one of these scopes, In-House, no PR. Its "Assignment" section adds the Aljeel engineers (each supervisor or executor), the field-work dates, "vehicle required" and "advance required" (a "not required" answer needs a reason), and a derived **Ready to mobilize** (approved, vehicle reserved or not required, advance actually disbursed or not required). These fields have no Master column; the PR-PO export is unchanged.
  - Two new registers, each with its own matrix row: **Car Dispatcher** (vehicles and bookings; a vehicle can never be reserved twice for overlapping dates; one booking opens per approved assignment, more can be added; extension or new request) and **Financial Advances** (individual by default, group with one named custodian; requested, approved and disbursed amounts, expenses with receipts approved by the Finance L2 and never by the custodian, settlement with a derived balance; top-up or extension linked to the original; may stay open after the work closes; LYD only; amounts visible only to Finance, the Project Manager, the custodian and the custodian's Team Lead). The Car Dispatcher has nothing to do with the Warehouse DN/RN dispatch. Advances are field custody only, not project accounting. Neither register is part of the Master-format export.
  - Approving an assignment at L2 opens the booking and the advance requests together. Workflow tasks MOB-1 (stage 1), MOB-2 (stage 2, after B2) and MOB-5 (stage 5) follow "Ready to mobilize"; they count toward no milestone and sit in no gate condition, so milestones, gates, weights and existing SLA are unchanged.
- **SITE 360 and streams (owner decision 2026-10-29).**
  - The Sites module is named **SITE 360**.
  - It has a **stream filter** and one **sub-section per stream**. A sub-section shows and works on the sites' status in that stream only: its tasks, current step, late items and milestone.
  - **Navigation (owner decision 2026-11-05).** SITE 360 is a main menu of its own: "All sites" (the whole site data) and six sub-menus, each limited to its boundaries: Design & Acquisition (stage 1), Civil Works (2–4), Installation TE (5–8), Handover & Closure (9–10), Dismantle (the Dismantle register, E1–E3) and O&M (after HOTO: TE DLP/FAC and Final Closure; it overlaps Handover & Closure on those, accepted). Every register (Procurement, GECOL, HLC, Permits & HSE, Warehouse, Quality, Issue Log, Risk Register, Change Control Log, Readiness & Handover, As-Built, Meetings, RF & Design, Acquisition, Contractors, Car Dispatcher, Financial Advances) sits under the main menu **Registers & Logs** (السجلات والقيود).
  - Default streams are seed data, admin-configurable and versioned with the workflow:
    - Design & Acquisition: stage 1;
    - Civil Works: stages 2–4;
    - Installation (TE): stages 5–8;
    - Handover & Closure: stages 9–10.
  - Spec: `docs/spec/registers-and-streams.md`.
- **Two entry ways everywhere (owner confirmation 2026-10-29).** The SITE 360 and every other register accept either manual entry or an approved template (download, fill, upload the same template). Both go through L1 → L2.
- The Audit Log records every user action with before and after values. It is append-only and nobody can edit it. The System/Error Log is kept separately.
- Audit Log readers (decision B4): System Admins and the Project Manager see all of it. Each Team Lead sees the entries for their own modules and regions only. Anyone else gets it only through the `view_audit` grant in the permission grid, scoped like any other grant (B3). Every read of the Audit Log is itself audited.
- **Messages and announcements (owner decision 2026-10-28, ADR 0013).**
  - Each user may have a **direct manager** and a **department** (an admin-managed list), set by the System Admin or a delegate on the Users & Roles screen.
  - **Messages:** a thread between an employee and their direct manager (either side may start it); a System Admin may write to anyone. Only the two participants can read it. The original message shows first, then the replies newest first. Messages are never edited or deleted.
  - **Announcements:** sent by a System Admin or a delegate (`announcements.create`) to everyone, or to chosen users, groups, roles and departments. The recipients are fixed when it is sent. Each recipient must answer in a **blocking pop-up**: agree, or disagree with a mandatory note. Answers are final.
  - The sender and the System Admins see the results (counts, answers, notes, who has not answered) and can export them.
- The UI is in English by default, with Arabic (RTL) available as an instant switch. It has light and dark themes and uses the Cairo font, with ERPNext (frappe-ui) colors.

## Decisions agreed with the product owner (2026-10-24)
Stack and platform
- NestJS with PostgreSQL. Hosting is on an internal server, never cloud.
- Login is Microsoft 365 (Entra ID) for Aljeel employees only. Vendors, contractors, GECOL, HLC and suppliers never log in. Staff enter their data and upload their documents for them, and every task still shows the external party responsible for it (for example A&T Global) so delays are attributed correctly.
- Two-factor authentication: enforced through Entra Conditional Access. The API checks the token's `amr` claim for `mfa` behind an admin toggle (off until IT enables MFA). Step-up re-authentication is required for final approval, role/matrix/group changes, delegation, deletes and admin overrides. One break-glass local admin account exists, with TOTP, usable from the internal network only, and every use is logged and emailed. **Per-user MFA exemption (owner request 2026-10-25):** a System Admin (or a delegate granted it) can remove GSDN Workspace MFA requirement for any registered user, until revoked or until an end date. The exempted user then signs in and passes step-up without `amr = mfa`. It needs a reason and the acting admin's own step-up MFA, nobody can exempt themselves, it is audited with before/after values, the user is emailed, and the Users & Roles screen shows an "MFA exempt" badge. It removes only GSDN Workspace check; MFA enforced by Entra Conditional Access is changed by IT in Entra, not in GSDN Workspace.
- Notifications go in-app and by email.

Roles, groups and administration
- **Staff registry (owner request 2026-10-25, settles B13).** A registry of Aljeel staff holds employee ID (4 digits), name EN/AR, phone, email, position, team and region. It is the list checked at first sign-in: the entered employee ID must exist in the registry and not already be linked to another account. A draft with synthetic rows is seeded and replaced with real data later. Wherever a person is shown as holding a task (task grid, drawer, Approvals, My Work, matrix), their employee ID is shown beside the name; hovering or focusing it opens a small card with the registry data. Phone and email in the card follow visibility settings kept in the registry screen: by default every signed-in Aljeel employee sees them; the admin (or a delegate) can choose which roles, groups or persons see or do not see each field, and can hide a field for a single employee. Maintained by the System Admin or a delegate, imported from an approved template, audited, never hard-deleted. Owned by the `people-registry` agent.
- Users & Roles screen. A user signs in with M365 the first time and enters a 4-digit employee ID. The account stays "Pending assignment" and sees nothing until an admin assigns its main role, sub-roles, team (CW/TE/both), permission level (view / L1 / L2 / admin), regions, visible modules and status.
- **Role assignment is many-to-many and works in both directions.** By role: pick a role (main or sub-role), then multi-select any number of registered employees by name (searchable list of everyone who signed in with M365), for example 12 Site Engineers in one action. By person: one employee can hold several main roles and several sub-roles at once. Each assignment row carries its own permission level, regions, modules and validity dates, so the same person can be an approver in one role and a data-entry user in another. Bulk actions include assign, remove, copy the assignments of one person to another, and an import from an approved Excel template. Every change is audited. **Overlaps (owner answer Q18, 2026-11-04):** two rows of the same person and role may not overlap in dates while sharing a region and a module; rows for other regions or modules are independent, and a bulk action skips the overlapping ones and shows the conflicts. The database refuses an overlapping row too (deferred check, 409 `already_assigned`; technical decision Q300, migration 0066).
- Groups: named sets of users (for example "System Admins", "CW Approvers Tripoli"). A matrix cell (L1 or L2) accepts users, roles, groups or a mix. A task assigned to a group shows in every member's inbox; the first member to act claims it. Default rule is any one member; it can be set per cell to "all members must approve". (Decision B10) Under "all members must approve", one member's rejection rejects the task and sends it back with that note. A task whose level has no eligible holder (for example an expired assignment with no replacement) goes to the System Admins' inbox with an immediate alert and shows on the dashboard as "no holder"; it is never skipped automatically.
- System Admin is a group (one or more people) with full control. An admin can delegate full or partial rights, either time-bound or until revoked. A delegate cannot re-delegate or remove an admin, and at least one active admin must always exist. Every action by a delegate is logged as "X on behalf of System Admin".
- Admin overrides are all allowed: unlock a stage or task, skip or mark N/A, accept without document or workflow, reopen an approved task, edit any date, and change the rules (documents, SLA, templates, gates, L1/L2 holders, QC photo rules) from settings screens without code. Each override requires a reason and step-up MFA, is written to the audit log with before/after values, shows an "Admin override" badge, is reversible, and is excluded from or flagged in KPIs.
- **Direct admin edit (decision 2026-11-12 (2), migration 0088).** A System Admin (never a delegate) edits any site field at once (names, coordinates, region, cluster, scenario, scope flags, custom fields; the Site ID is immutable) and any task date (`POST /sites/{id}/admin-edits`, `POST /tasks/{id}/overrides` kind `edit_date`), with a reason and step-up, one audit row with before and after, the "Admin override" badge, and `POST /overrides/{id}/revert` while the field still holds what the override set. Non-admins keep the Change Control proposal path.
- The seeded roles are plain roles (no parent role, owner decision 2026-10-29), editable in the UI.
- Approval always has two levels: L1, then L2, for every stage, register and Dismantle (owner decision 2026-11-01). The admin chooses the holders, not the number of levels.

Configuration owned by the System Admin (or a delegate)
- **Every create, rename, edit, deactivate or delete of configuration is a System Admin action**, or that of a person the admin delegated it to. Examples are task definitions, fields, lists, documents, templates, SLA, weights, warehouse items and roles. The Roles & Responsibilities settings decide who may do what. Each change is audited with before/after values, needs a reason, and is versioned. Nothing referenced by data is hard-deleted; it is deactivated.
- **Delegation covers anything, to anyone.** The System Admin can delegate any action in the permission grid (including configuration: warehouse items, task definitions, custom fields, lists, documents, templates, SLA, weights, workflow versions, roles and permission profiles) to any person, any role or any group, for all regions or selected ones, time-bound or until revoked. Delegation is configured in the Roles & Responsibilities settings and is simply a permission grant. The database checks every configuration write against the actor's effective permission (`app_has_permission`), not against a fixed admin flag, so a delegated person can do exactly what was delegated and nothing more. Safeguards stay: nobody can grant rights to themselves, a delegate cannot re-delegate unless the admin explicitly allows it for that delegation, a delegate cannot remove an admin, there is always at least one active admin, and every delegated action is logged as "X on behalf of System Admin".
- **Warehouse item master data** (item names, units, categories, design-based need rules) is edited by the System Admin, and by the Inventory Supervisor only through delegation from the admin.
- **Items and work fields are data, never fixed columns (owner decision 2026-10-29).**
  - **Warehouse items:** added, renamed, edited and deactivated in the Warehouse register by the System Admin or a delegate. This covers name EN/AR, code, unit, category, serial tracking and need rules. Items are never deleted while used.
  - **As-Built items:** the CW quantities and the TE configuration items are an editable item list, not fixed columns. They are added, renamed and deactivated in the As-Built register, with the same rights as above. Each As-Built item can be linked to a Warehouse item code (Q74).
  - **CW and TE work fields:** the work entry fields of the CW and TE stages, in tasks and in their registers, can be added, renamed and edited through the custom-fields rules below.
  - Every change is audited and versioned. Templates regenerate with a new version, and the Master-format export keeps each item's Master column when it has one.
- **Task definitions are editable.** The admin can add new tasks or sub-steps inside any existing stage (for example a new step in PRE-CW or CW, or in TE), and can rename, reorder, change predecessors, or deactivate tasks. A new task gets its SLA rule, Document Library slots, template and matrix cells like any other task. Milestones and phase gates are also configurable (see the next rule). Each task has a flag "counts toward the stage milestone" (default yes), so the admin decides whether a new task blocks the milestone. (Decision B8) When a new counting task is added, the screen warns that the milestone date may move later than the Master; during the parallel-run month the admin must confirm explicitly, and the comparison report tags the resulting date difference "caused by an added task" so it is not counted as an import error. Changes apply to new site tasks. For open sites the admin chooses whether to add the new task to them.
- **Milestones and phase gates are configurable by the admin (decision 2026-10-25, replaces "fixed").**
  - **Light changes, applied immediately:**
    - rename (EN/AR display names)
    - custom fields on milestones and gates
    - the gate conditions (which tasks, permits or dates a gate waits for)
    - the gate SLA
    - whether a milestone counts in Project Status
  - **Structural changes** (add, remove or reorder a milestone or gate, or move tasks between stages) are published as a new version of the workflow definition, with a reason and step-up MFA.
    - New sites use the new version. For open sites the admin chooses, per site or in bulk, whether to migrate them; the migration preview shows which tasks move and which dates change.
    - Sites never silently change version.
  - Every milestone and gate keeps a stable internal code, so renames never break history, KPIs or reports. Each one also carries its Master export column.
  - The screen warns when a change affects the Master-format export or the parallel-run comparison. During the parallel-run month the warning requires an explicit confirmation.
  - Project Status and the dashboard read the active workflow version per site.
  - **Freeze during pilot and parallel run (decision B9):** structural changes are blocked from the pilot start to the end of the parallel-run month. Only a System Admin can lift the freeze, with a written reason and step-up MFA, and the lift is audited. Light changes, and new tasks inside an existing stage (B8), stay allowed.
- **Roles are fully admin-defined.** The seeded roles are seed data only. The admin can create a new role with:
  - a name (EN/AR) and a description of its duties
  - a default permission profile
  - default regions and modules
  - whether it may hold matrix levels (L1 / L2)

  Example: a **Management** role with "view the dashboard and progress reports", read-only on all modules and all regions, and no entry or approval. Roles can be renamed or deactivated (never deleted while assigned). Every change is audited.
- **Custom fields (like adding a column to the Master).** The admin can add fields to any register (Procurement PR/PO/WO, GECOL power, HLC fiber, RF survey and design, Acquisition, Permits, Warehouse, Quality, Issue, Risk, Change Control, Readiness & Handover, As-Built, Meetings), to sites and to tasks. Each field has: label EN/AR, type (text, number, date, list, multi-list, yes/no, user, external party, file), required or optional, validation (min/max, pattern), list values (themselves editable), default, order and section, which roles can see and which can edit it, whether it appears in templates, exports and the Master-format export (with its column), and whether it is shown in lists and filters. Fields are versioned and deactivated, never deleted, so their history is kept. Templates regenerate with a new version when fields change, and old template versions are rejected on upload with a clear message.

Permissions (part of Roles & Responsibilities settings)
- Beyond the matrix (L1 / L2), each role or assignment has a **permission grid per module and screen**: view, create, edit, delete, approve, export, import, download documents, see the audit log, and administer. Optional **field-level** rules hide or make read-only specific fields, including custom fields. Navigation shows only what the person may use. Permission sets can be saved as named profiles and applied to many assignments. Effective permission (decision B3) = union of the person's active assignments, each assignment limited to its own regions and modules. Scopes never cross: a CW role in Tripoli plus an approver group in Zawia shows CW in Tripoli and the review work in Zawia, not CW in Zawia. All of this is configured in the Roles & Responsibilities settings and audited.

Business rules
- SLA for D-1 (TE Access) is measured from TE Installation Readiness (the Site RFI date), not from Site Release.
- Expansion scenario: Site Release keeps TSSR and LLD only. PRE-CW and CW apply only when adaption work exists. Power-On and TX test apply only if new power or fiber is needed. TE through Final Closure all apply. Conditions are decided by the Master scope flags (AA:AF).
- Cluster: use the Master rule. Each site's optimization gate opens from its own TE PAC. KPI Acceptance is recorded once per cluster and applied to all its sites. The site page shows cluster progress ("6 of 9 sites at TE PAC") as information only.
- Project Status stays as it is, ending at HOTO. Final Closure gets a separate KPI: sites closed, % closed, and pending CW FAC / TE FAC with their age.
- Site RFI has no document. Its date field unlocks when its conditions are met, is pre-filled with the latest condition date, can be edited, and then goes through review and approval.
- **SLA is fully editable by the admin, without code.** Each task has an SLA rule with a minimum and a maximum in working days (min = target/green, max = limit; above max = late), the start event it is measured from, and the calendar (weekend days and the holidays table). Optional overrides by delivery scenario or region are allowed. Rules are versioned with an effective date, a reason, and the person who changed them, and every change is audited. A task keeps the SLA version that was in force when it opened, so changing an SLA never rewrites past KPIs. When publishing a change, the admin can choose to apply it to tasks that are open now.
- **Project Status weights are editable by the admin, without code.** This covers the 8 activity weights (default 12/8/5/25/20/12/13/5), the weights of the 45 items within each activity, and each item's unit and measure. It also covers the other weighted formulas, the health index and delay attribution. The screen validates that weights sum to 100% at each level before publishing. Weight sets are versioned with an effective date, a reason and the person who changed them, and every change is audited. Current progress is recalculated with the active set. Saved weekly snapshots keep the values computed at the time, and a report can be re-run with an older weight set for comparison.
- PMIS-only features: delay attribution and project health index are in version 1. HSE incidents and clock-in are deferred to the mobile app. Team capacity and certificates are dropped.

Documents and QC
- **Acceptance documents and QC photos are different things.** Acceptance documents (TE PAC, SSV, CW FAC, TE FAC, HOTO and so on) are the official forms, filled, signed, scanned and uploaded. They close their task through the approval workflow. QC photos are photos of a fixed defect. Wherever a QC check or snag exists, the site engineer uploads fresh photos of the fix, then the L2 approves, which closes that snag.
- An acceptance cannot be approved while a snag of its own stream is open on the site (owner decision 2026-10-29): open CW snags block CW PAC and CW FAC, open TE snags block TE PAC and TE FAC. Its lock reason shows the count. A FAC cannot be generated before its DLP ends.
- QC photo requirements are configured per snag type: minimum count, required shot types, formats (JPG/PNG/HEIC), and maximum size. Photos taken before the snag was raised are rejected using the EXIF date. A missing EXIF date is accepted with an "unknown capture date" flag for the L2.
- **Document Library (admin).** Every document is defined in data, never in code: name EN/AR, kind (scanned document, photo, email, report, approved Excel template), placement (one or more tasks, QC, or a register), mandatory or conditional (with the rule), formats and size, minimum/maximum files, photo rules, expiry date, and an optional blank form to download. On publish, the admin chooses whether it applies to new tasks only or also to open tasks. Approved tasks never change. Documents are deactivated, never deleted.
- Seed content of the library: Stage 1 has A1 SAR (each candidate), A2 TSSR, A3 owner contract (or contract with the tower owner for an existing third-party tower) plus a civil aviation permit when near an airport, and A4 LLD. Stage 2 has B1 PR email (outsourced only), B2 PO/WO email or internal work order, B3 CW access permission, B4 STA/ST report (when tower analysis is required; it sits on task B5), B6 layout, and B7 approval email and CW DN. Stage 3 has B9 MOS proof; B11 has no document, and defects become QC snags. Document codes are document codes: each document sits on its real task code (owner answer Q129). Stages 4 to 10 are seeded from blueprint v1.0 and the Master, then reviewed by the product owner in the library screen. The default for every document is PDF or image, 20 MB, multiple files allowed.
- Upload UI uses one named slot per required document, showing status (missing, uploaded, in review, approved, rejected with reason). Files can be dragged onto a slot, clicked, or taken with the phone camera. For a multi-file upload, the type is suggested from the file name and confirmed in a dropdown. Conditional slots appear only when they apply. "Submit for review" stays disabled until every mandatory slot is filled.
- Download is available from the task, from the site Documents tab (filterable), and in bulk as a zip (per site, per stage, or per document type across sites). Superseded versions are kept and downloadable. Files are named automatically `SITE_TASK_DOC_APPROVEDDATE.ext`. Every download is written to the audit log.

Generated documents (forms issued by the system)
- **Default approver (decision B2):** the stage's main role approves (for example CW Team Lead for CW stages, TE Team Lead for TE stages), and the Project Manager approves Final Closure. This is seed data and is editable in Roles & Responsibilities.
- **CW forms are issued by the system**: CW DN (material delivery to the contractor or site), CW RN (return note), CW PAC, CW FAC and the Snag list. Each is a Document Library entry of kind "generated form" with:
  - a form template the admin can edit. The owner's approved CW forms are HTML (`design/forms/source/`), so templates are HTML with placeholders and repeating blocks, rendered to PDF by headless Chromium on the internal server. The admin can upload a new template version; each generated PDF records the template version it used;
  - data bindings (site, contractor, dates, signatories from the matrix, warehouse lines with quantities and serials, snag list);
  - a numbering sequence (for example `DN-CW-TR-2026-0001`, configurable);
  - a QR code that links back to the record.
- **Flow**:
  1. The responsible person prepares the record. For DN/RN this is the warehouse movement lines; for PAC/FAC it is the site data and snags.
  2. The system generates the numbered PDF.
  3. The PDF is printed and signed on paper.
  4. The signed scan is uploaded into the same slot.
  5. The upload goes through the approval workflow.
- **Item tables come from the system, not from the form.** The DN and RN line tables are built from the warehouse movement lines (item master: description, UOM; quantities approved, dispatched or returned; serials when tracked). Only items with a quantity are printed, plus a configurable number of blank rows. The fixed 28-item lists in the source forms become seed data for the CW item master. The PAC "Accepted Item List (BoQ)" prints the CW As-Built quantities (owner decision 2026-10-29), with a warning per item where the net DN minus RN differs. The PAC acceptance checklist is entered in GSDN Workspace and printed filled. The PAC snag list comes from the site's QC snags with their closure status. FAC references its PAC automatically.
- **Pre-filled vs signed by hand.** The system fills every data field: ref no., dates, site, region (checked), contractor, PO/WO, warehouse, quantities, snags, and the names and positions of signatories from the Responsibility Matrix. Signatures and stamps stay blank for wet signature, and the signed scan is uploaded back into the same slot.
- **Warehouse link**: an approved DN posts the stock issue to the site, and an approved RN posts the return. Until approval, the quantities show as "pending issue" or "pending return", and stock is reserved so it cannot be issued twice.
- **Guards**:
  - CW PAC cannot be generated while any CW snag on the site is open.
  - Numbers are never reused or deleted. A wrong form is voided with a reason and reissued with a new number.
  - Every generation, void and download is audited.
- **TE forms are deferred.** Each TE document will be classified in the Document Library as one of: issued by Aljeel (generated by the system), issued by the vendor (uploaded only, with its metadata fields), or jointly signed (generated by the system, signed by both parties). The classification is agreed with the owner later and needs no code change.

Defects Liability Period (DLP)
- Defaults: CW 3 months, TE 12 months, counted from the PAC date. Each is a System Admin setting (`dlp.months.cw`, `dlp.months.te`), versioned; a PAC keeps the value in force when it was issued.

Self-approval (decision B5)
- If one person holds both L1 and L2 of a task (granted together in Roles & Responsibilities), their submission becomes the final approval. It needs step-up MFA, is flagged "self-approval" in KPIs and the audit log, and the matrix screen shows the case in advance.

Mobile app (later, design for it now)
- A site engineer sees only the tasks assigned to them. The in-app camera stamps every photo, visibly and in metadata, with site ID, name, address, registered coordinates, device GPS, date/time, engineer, and task.
- The geofence check flags a photo taken more than 300 m (configurable) from the site. Proof tasks (MOS, QC) accept the in-app camera only. Capture works offline and syncs later with the original timestamp.

Administration screens (owner approval 2026-10-26, patterns taken from a reference system; our rules win where they differ)
- **Notification policy** in Settings: on/off, timezone (Africa/Tripoli), daily digest hour, thresholds with allowed ranges (approval reminder and escalation, SLA warning, rate cap per hour, retention), and a matrix of notification type × role/group with channels (in-app, email). Some types are mandatory and cannot be turned off (audit integrity failure, retention reduced). Security and system types go to System Admins only. Versioned and audited like other settings.
- **Every settings save rejects unknown keys and returns field-level errors**, including rules across fields (for example, escalation must come after the reminder).
- **Sign-in and security log**, separate from the Audit Log and the System/Error Log, readable by System Admins or the `view_security_log` grant; every read is audited. An identifier typed in the sign-in box that matches nobody is never stored as typed (it may be a password): only a masked keyed hash is kept, so repeated attempts can still be grouped.
- **Log integrity check**: the Audit Log and the security log are append-only hash chains; an admin button verifies each chain and lists any break.
- **Online now**: admins see active sessions (status, last activity, current screen) and can end a user's sessions with a reason and step-up MFA. Background polling never extends the idle timeout.
- **Log retention**: System Log and security log retention are settings with a minimum (90 and 365 days); reducing one needs a reason and step-up and raises a mandatory alert. The Audit Log stays 10 years and is not settable.
- **Typed confirmation** (type the target's code or name) is required, in addition to step-up MFA, for lifting the structural freeze, publishing a workflow version and dismantle.

Rollout
- A pilot on one region (Tripoli) runs for 2 weeks. Then the system and the Master run in parallel for 1 month: GSDN Workspace exports a Master-format file and it is compared automatically with the live Master. The Master is retired after one month without material differences.
- Training is per role: short Arabic videos, an in-app guide on first use, one live session per role group, and a Project Support champion.
- Acceptance criteria: critical-path E2E tests pass, the real Master import matches 100% of milestone dates, no open critical bugs, and the performance targets are met.
- Real data is uploaded through the system after it is complete.
- **Full project export to a Master file, on demand (owner request 2026-10-25).** Any user with the `export` grant can download, at any time, the whole project data as one Excel file in the exact Site Master layout (all sheets and the 187 columns, plus custom fields that carry a Master export column). It runs as a background job and the file is offered for download when ready. The content is limited to the caller's regions and modules (B3); a System Admin gets everything. The same export feeds the parallel-run comparison. Every export and download is audited.
  - **Full or partial, chosen from a list (owner request 2026-10-25).** The export dialog offers "Whole project (full Master)" or a multi-select list of parts: each register (Procurement PR/PO/WO, GECOL, HLC, Permits & HSE, Warehouse, Quality, Issue, Risk, Change Control, Readiness & Handover, As-Built, Meetings, Contractors), Sites and milestones, tasks by stage, Project Status, Dismantle.   - Partial exports keep the Master sheet and column layout for the chosen parts, so they can be compared with or pasted into the Master.

## Working agreement between agents
- **Contract first.** No endpoint is built before it exists in `contracts/openapi.yaml`. The web app uses MSW mocks generated from the contract until the API is ready.
- **Own your folders.** Each agent writes only inside its own folders (see `ORCHESTRATION.md`). Changes needed elsewhere go as a request to tech-lead.
- **Small PRs** to `develop`. Each PR includes tests and a short note covering what changed, how it was tested, and any open questions.
- **Every piece of work ends in a pull request with comments (owner instruction 2026-10-28).** Never leave pushed work without a PR: open one (or update the open PR of the branch) with a description in the sections what changed / security / how it was tested / open, and post a comment that points the reviewer to the parts that need a careful human review (permissions, passwords, grants, migrations). After each later push to the same branch, add a short PR comment saying what the push changed. Follow the PR afterwards: fix CI failures and answer review comments.
- Never invent business rules. If the spec is silent, add the question to `docs/spec/open-questions.md` and use a configurable default.
- Use only synthetic data (fictional names) until the product owner releases real data. Never commit secrets.
- **Keep `CHANGELOG.md` current.** Every PR that changes a decision, the spec, the schema, the contract, the design or the forms adds a dated entry at the top under the right heading (قرارات, إضافة, تعديل, أمان, مفتوح).
